title-first loading shells could satisfy browser readiness before the actual

## Skills contract and review blockers

The initial spec review confirmed two P1 acceptance gaps observed in the
[Shutterfly walkthrough](../shutterfly-live-job-attempt-2026-11-09.md):

- [SL-BUG-002](../implementation/sentilink-followups/bugs/sl-bug-002-skills-operation-contract.md):
  fresh runner output lacked required before/result list intent, permitting
  an inverted prune while displaying contradictory wording.
- [SL-FEAT-001](../implementation/sentilink-followups/features/sl-feat-001-skills-review.md):
  unified review could not select the skills editor; Changes displayed prose
  rather than the actual list effect.

Fresh Jobs and Tailor generation now require captured before and intended
result lists, plus an explicit whole-group removal choice. Policy
`accomplishments-2` validates stale targets, list membership, duplicates,
permutations, no-ops, empty groups, and overlapping operations. Fresh model
output cannot supply authoritative decisions, checks, or overrides. Tailor
persists server-owned policy on the proposal step; save, draft Apply, and
reload cannot downgrade it or override a structural skills failure.
New pending runs capture the policy before generation. Recovery derives policy
from the server-held parent record and associated manifest, never client
snapshot metadata. Fork publication guards both lineage files against changes.
Missing, corrupt, disassociated, or unknown lineage uses the current contract;
trusted legacy recovery retains its established policy.

Existing saved proposals remain readable without regeneration. Legacy policy
and absent-policy Tailor runs retain their established operation and human
override semantics; explicit regeneration opts into the fresh contract. Strict
draft persistence retains the new intent and source fields.

Unified resume review includes selectable skills passages. The editor supports
pruning, reordering, and explicit whole-group removal, with container-aware
controls on desktop and mobile. Changes compares actual list effects, supports
save/reload and undo, and preserves unrelated wording and following groups.
Inherited skill lists are explicitly described as list review, without claiming
that each inherited skill has independent evidence verification.

The first implementation review caught two further gaps: the older Tailor
runner bypassed fresh admission, and desktop sidebar columns clipped skill
names and badges. Both were corrected before the second integrated run.
Actual runner tests cover retry, machine overrides, policy spoofing, manual
save, draft Apply/reload, and legacy reopening without runner calls. Real
Chromium layout tests check painted text and control bounds for prune and
reorder in desktop sidebar, mobile, and wide containers.

## Preparation performance blocker

The initial full suite failed the seven-job automatic-preparation scenario:
1,805 tests passed, one skipped, and one timed out. An isolated rerun reached
only six ready jobs within its 15-second wait. The deadline, assertions, and
preparation budgets were not relaxed.

Profiling found that queue reads generated complete download bundles merely
to establish export validity, repeatedly reading and validating the same
immutable bytes. Queue reads now use the same export resolver under a
request-scoped file-read scope, without compiling download formats. Download
compilation also shares validated reads within its own call. There is no
persistent cache; subsequent requests still detect changed privacy rules,
source evidence, input bindings, semantic state, templates, and tampered bytes.

One controlled synthetic seven-job profile improved from 16.135 to 7.892
seconds overall; cumulative queue-read time fell from 10.019 to 1.653 seconds.
These measurements diagnose the fixture rather than predict live runner speed.
Regression tests verify that queue validation avoids export compilation and
still rejects changes between reads. The original preparation tests are
unchanged and pass after the correction.
